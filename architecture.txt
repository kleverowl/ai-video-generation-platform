# Complete Video Generation Platform – System Architecture & Infrastructure Plan

Proposed architecture Low-cost, on-demand GPU

Objective: Build a web-based AI video generation platform that supports Instagram Reels, YouTube videos (including 2–3 minute and longer videos), and other user-selected video formats, while minimizing infrastructure and GPU costs.

The central principle is to keep the web application online using the existing Oracle VPS, but rent GPU computing only when a video-generation job needs it.

# 3. Oracle VPS – Web application and central management

Your existing Oracle Always Free VPS will remain online continuously.

Available resources:

- 2 vCPU
- 12 GB RAM
- 200 GB SSD

It will be responsible for managing the entire platform, not generating AI videos.

### Software running on Oracle VPS

| Software | Responsibility |
| --- | --- |
| Next.js | User interface and web application |
| Backend API | Receives and manages requests |
| PostgreSQL | Users, jobs, settings and metadata |
| Job queue | Maintains pending video-generation requests |
| Job orchestrator | Communicates with Google Cloud |
| Status manager | Tracks processing progress |
| R2 integration | Creates signed download links |

### What happens when a user requests a video?

1. User logs into the application.
2. Selects the video format.
3. Chooses duration, aspect ratio, voice and other options.
4. Submits the generation request.
5. Oracle creates a unique job ID.
6. The job enters the processing queue.
7. Oracle triggers a Google Cloud Run Job.

Oracle does not need a GPU to perform these operations.

### How GPU execution works

The GPU will not remain running permanently.

For each video-generation request:

1. Oracle submits a Cloud Run Job execution.
2. Google provisions the GPU resources.
3. The container starts.
4. The worker initializes its software.
5. AI models are accessed and loaded.
6. Video generation begins.
7. Generated assets are uploaded to R2.
8. The job exits.

Once the execution ends, GPU, CPU and RAM billing stops.

There is no need to manually shut down the GPU or send a shutdown signal from Oracle.

Important: Cloud Run Jobs are finite executions, not permanently running GPU servers. A new execution is required for a new independent job.

Never run LTX-2.5 and VoiceStudio simultaneously on the same GPU.

The execution should be sequential:

The worker can use one shared GPU execution to process the different stages.

### How model storage works

- Upload AI model files to Google Cloud Storage once.
- Keep the bucket permanently.
- Give Cloud Run workers permission to read the models.
- Mount the bucket into the container using Cloud Storage FUSE or implement controlled downloading and local caching.
- Load models into system RAM and GPU VRAM when needed.

Important storage consideration: Google Cloud Storage is not a local SSD. For reliable high-performance model loading, I recommend copying the required model files to temporary local storage before inference, rather than relying on repeated random reads directly from a mounted bucket.

Also, Cloud Run's writable filesystem is ephemeral and memory-backed. Large temporary model copies need careful RAM and storage planning. The 16 GiB system RAM allocation is not automatically an additional 50 GB SSD.

The model bucket remains available even after the GPU job terminates.

R2 will store:

- Generated video clips.
- Voice audio.
- Background music, where applicable.
- Intermediate assets needed for rendering.
- Final MP4 videos.
- Thumbnails and previews.

### Why R2?

- No need for a permanently running storage server.
- No conventional internet egress charge for downloads from R2.
- Suitable for user downloads.
- Storage scales with actual usage.

Use signed URLs or an authenticated download endpoint to control access to users' videos.

# 8. Video rendering architecture – Remotion and FFmpeg

AI generation and final video assembly are separate operations.

LTX generates the video clips. VoiceStudio generates the audio. Remotion combines everything into the final timeline.

### Rendering workflow

text

```text
Generated video clips
        +
Generated voice audio
        +
Background music
        +
Captions / subtitles
        |
        v
   Remotion Timeline
        |
        v
     FFmpeg
        |
        v
 Audio loudnorm
        |
        v
  Final MP4 Video
        |
        v
   Cloudflare R2
```

### Where should rendering happen?

My initial recommendation is to use a separate CPU-only worker, without renting another GPU.

For the first implementation, this can be a Cloud Run CPU Job or another suitable CPU execution environment.

However, Remotion rendering needs adequate memory and CPU, particularly for longer videos and complex compositions. Benchmark it before fixing the final CPU configuration.

# 11. Automatic cost-control mechanisms

The following controls should be implemented from the beginning.

| Control | Configuration |
| --- | --- |
| GPU concurrency | 1 initially |
| Job retries | 0 initially |
| Job timeout | 60–90 minutes initially |
| GPU startup | On demand |
| GPU shutdown | Automatic on completion |
| Model storage | Persistent |
| Output storage | Persistent |
| Queue | Sequential |
| Failed jobs | Notify user and record failure |
| Billing alerts | $5, $10 and $20 thresholds |

A billing alert is a notification, not a guaranteed spending cap. Implement application-level limits as well.

# 12. GPU availability and fallback strategy

The architecture should not depend permanently on a single GPU provider.

| Priority | Provider | GPU | Region |
| --- | --- | --- | --- |
| 1 | Google Cloud Run Jobs | L4 24 GB | Singapore |
| 2 | Google Cloud Run Jobs | L4 24 GB | Mumbai, if access is granted |
| 3 | AWS Batch / EC2 | A10G 24 GB | Mumbai |
| 4 | Alternative GPU provider | L4 / RTX 4090 class | Based on availability and pricing |

The Oracle backend should communicate with GPU workers through a common job interface.

This means you can change the GPU provider without redesigning the frontend or the entire application.

A fallback should only be triggered for genuine capacity or availability failures, not blindly for every failed generation.

# 13. Security and permissions

- Oracle communicates with Google Cloud through a securely authenticated service account.
- Cloud Run uses a dedicated service identity.
- Model storage permissions are read-only.
- Output storage credentials are restricted to the required R2 bucket operations.
- Users can only access their own generated files.
- Download URLs are signed and expire.
- Secrets and API keys are stored outside Docker images.
- Job requests are validated before execution.

# 14. Deployment roadmap

I recommend implementing this in stages rather than building everything at once.

1. Phase 1 – Web application
   Deploy Next.js, backend API, database and job management on your Oracle VPS.
   Deliverable: Users can submit video-generation requests and track jobs.
2. Phase 2 – Storage infrastructure
   Create the Google Cloud Storage model bucket, Cloudflare R2 output bucket and Artifact Registry repository.
   Deliverable: Models and generated assets have permanent storage.
3. Phase 3 – GPU worker
   Build the ComfyUI + LTX Docker image and deploy one Cloud Run GPU Job in Singapore.
   Deliverable: One submitted job can generate a video and upload it to R2.
4. Phase 4 – Voice pipeline
   Add VoiceStudio and Whisper to the sequential GPU processing workflow.
   Deliverable: Generated videos include the required voice and audio processing.
5. Phase 5 – Video rendering
   Integrate Remotion and FFmpeg using a CPU worker.
   Deliverable: Complete videos are assembled and uploaded to R2.
6. Phase 6 – Production optimization
   Measure model loading, GPU generation, CPU rendering, network transfer and total cost per video.
   Deliverable: Reliable production pipeline with spending controls.

## Final architecture philosophy

The platform follows three simple principles:

1. Keep permanent infrastructure cheap: Oracle VPS hosts the web application, database and job management.
2. Pay for expensive computing only when needed: Google Cloud provides temporary GPU resources for video generation.
3. Keep files independent of computing: Google Cloud Storage preserves AI models, while Cloudflare R2 preserves generated videos and other assets.

The GPU is replaceable. The storage is permanent. The web application remains online.

This gives you a platform that can start with a handful of videos per month and scale up without requiring a complete architectural redesign.

One important production gate: Before accepting paid users, validate LTX-2.5's actual 24 GB VRAM requirements, model loading time, Cloud Run temporary storage capacity, GPU availability and commercial licensing for every model and voice used.
